## Unit tests — `test/wize-alias.test.js`

### UT-S10-01: `wize` alias skill file exists
```js
test('/wize alias skill file exists', () => {
  // The alias can be implemented as either:
  // (a) src/orchestrator-skills/wize/skill.md (redirect approach)
  // (b) a symlink src/orchestrator-skills/wize -> wize-help
  const aliasPath = path.join(KIT, 'src/orchestrator-skills/wize/skill.md');
  const symlinkPath = path.join(KIT, 'src/orchestrator-skills/wize');
  const exists = fs.existsSync(aliasPath) || fs.existsSync(symlinkPath);
  assert.ok(exists, '/wize alias must exist as skill.md or symlink');
});
```

### UT-S10-02: `wize` alias has valid frontmatter with `code: wize`
```js
test('/wize alias has code: wize in frontmatter', () => {
  const { readFrontmatter } = require('../tools/installer/render-shared.js');
  const aliasPath = path.join(KIT, 'src/orchestrator-skills/wize/skill.md');
  if (!fs.existsSync(aliasPath)) {
    // Symlink approach — resolve and read the target
    const target = fs.realpathSync(path.join(KIT, 'src/orchestrator-skills/wize'));
    // For symlink, the code comes from the symlink name, not the target's frontmatter.
    // The adapter must handle this. Skip the frontmatter check for symlink.
    return;
  }
  const content = fs.readFileSync(aliasPath, 'utf-8');
  const fm = readFrontmatter(content);
  assert.equal(fm.code, 'wize', '/wize alias must have code: wize');
  assert.ok(fm.name, '/wize alias must have a name');
});
```

### UT-S10-03: `wize` alias body redirects to `wize-help`
```js
test('/wize alias body references wize-help', () => {
  const aliasPath = path.join(KIT, 'src/orchestrator-skills/wize/skill.md');

});
```

```js
test('/wize and /wize-help render to equivalent SKILL.md content', () => {
```

## Implementation notes

### Approach A: Redirect skill.md (recommended)

Create `src/orchestrator-skills/wize/skill.md`:

```markdown
---
code: wize
name: Wize
module: orchestrator
owner: wize-orchestrator
status: ready
---

# /wize

This is an alias for `/wize-help`. All invocations of `/wize` are handled by the
`wize-help` skill. See `src/orchestrator-skills/wize-help/skill.md` for the full
implementation.

When invoked, delegate to `wize-help` with the same arguments.
```

**Pros**: Portable (works on Windows), explicit, can include alias-specific metadata.
**Cons**: Duplicates the skill listing (both `wize` and `wize-help` appear in skill lists).

### Approach B: Symlink

```bash
ln -s wize-help src/orchestrator-skills/wize
```

**Pros**: Zero duplication, automatically stays in sync with `wize-help`.
**Cons**: Not portable to Windows without developer mode enabled. May confuse git on some systems.

### Recommendation: Approach A (redirect skill.md)

The kit already has 73+ skills; one more small file is negligible. Portability across platforms is more important than avoiding duplication. The redirect body makes the alias relationship explicit and documentable.

### Files to modify

1. **Create**: `src/orchestrator-skills/wize/skill.md` — the alias skill
2. **Modify**: `tools/installer/render-shared.js` line 291 — change `Then ask \`/wize-help\`.` to `Then ask \`/wize\`.`

### Interaction with S08-c

S08-c removes the broken `/wize` alias that was referenced but never implemented. S10 adds it back as a real alias. These stories are in the same sprint and must be sequenced correctly:

- **If S08 runs first**: S08-c removes references to the broken `/wize`. S10 then adds the real alias and updates references. No conflict.
- **If S10 runs first**: S10 adds the alias. S08-c must NOT remove the newly-added alias — it should only remove references to the *broken* alias (which didn't exist). The test in UT-S08-07 must be scoped to pre-existing references, not the new S10 alias.

**Recommendation**: Run S08 before S10, or ensure S08-c only targets pre-existing broken references.

## Concerns

- **Finding**: The `wize` alias adds a second skill with overlapping territory. If a harness shows both `/wize` and `/wize-help` in its skill picker, users may be confused about which to use.
- **Impact**: Low — both route to the same behavior. The alias description can clarify: "Alias for /wize-help — use either."
- **Recommendation**: In the `wize` alias skill.md description, explicitly state "Alias for /wize-help. Both commands are equivalent."

- **Finding**: `collectAssets` will return both `wize` and `wize-help` as separate assets. This means `AGENTS.md` and all adapter renders will include both. The `AGENTS.md` roster section doesn't list skills — only agents — so this is not a problem there. But adapter renders will create two SKILL.md files.
- **Impact**: Low — two files instead of one. The alias file is small (~200 bytes).
- **Recommendation**: Accept the duplication. It's the cost of portability. If it becomes a problem, add a deduplication step in `collectAssets` that merges aliases.

- **Finding**: The onboarding one-liner (`→ /wize`) is primarily an S09 concern. S10 just needs to ensure `/wize` works. If S09 hasn't run yet, the onboarding test (UT-S10-06) may need to be scoped to just verifying the reference exists, not that it's a one-liner.
- **Impact**: Low — S09 depends on S10, so S10 ships first. The test should verify the reference exists; S09 will tighten it to a one-liner.
- **Recommendation**: UT-S10-06 should use `assert.match(out, /\/wize\b/)` — just verify the reference exists. Don't assert on the format (one-liner vs multi-line) since that's S09's responsibility.
